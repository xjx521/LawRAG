### Q1：为什么后端要分层？不分层会怎样？

**分层的规则**：

```
api  →  services  →  core  →  models
（薄）   （编排）    （内核）   （数据）
```

**单向**：上层可以调下层，下层**不许**反过来调上层。

**如果不分层的真实后果**（不是理论）：

- 路由函数里直接写 SQLAlchemy 查询 → 想给检索逻辑写单测，必须起一个 HTTP 服务器
- `core/retrieval` 里 `import` 了 `api.v1.chat` 的某个工具函数 → 循环 import，Python 直接崩
- 三个月后想换一个向量库，要改 20 个文件

**关键认知**：`core/` 是**内核**——它不该知道 HTTP 的存在。给它一个 `query: str` 和一个 `kb_id: int`，它返回检索结果。至于这个调用是来自 HTTP 请求、CLI、还是定时任务，`core` 不关心也不知道。

**怎么保证不退化**：`import-linter`。人靠自觉一定会烂，尤其是赶进度的时候。

> 类比：`core` 像发动机，`api` 像方向盘和踏板。发动机不该知道方向盘长什么样——你把它装船上也应该能转。

### Q2：为什么 Provider 要抽象？直接 `import` 不是更简单吗？

**看起来**：`core/llm/` 直接写 `from langchain_ollama import ChatOllama`，一行就完事了。

**实际上**：ADR-004 已经确定了要能切本地/云端，ADR-005 已确定了 rerank 有三个实现。**切换是既定需求，不是臆想的需求。**

**抽象的代价 vs 收益**：

| | 直接 import | Provider 抽象 |
|---|---|---|
| 写第一版 | 快（1 行） | 慢（写接口 + 2 个实现） |
| 切模型 | 改代码、全局搜替换 | 改 `.env` 一行 |
| 评估对比实验 | **做不到"一次只改一个变量"** | 配置切换即可 |
| 单测 | 要真连 Ollama | 塞个假实现就能测 |

**最后一条最容易被忽略**：论文要跑"有 rerank vs 无 rerank"的对照实验。如果重排是硬编码的，这个实验根本做不了。所以 `NoopReranker` **不是"以防万一"，是实验设计的一部分**。

> ⚠️ 这是本项目第一个"看起来过度设计，其实不是"的地方。面试官会问——**你要能答出上面这张表**。

### Q3：统一异常的意义是什么？

**不加统一异常**会发生什么：

```python
# 路由里随手 raise
raise HTTPException(404, "知识库不存在")     # 有的地方这样
raise HTTPException(400, "kb not found")     # 有的地方这样
return {"code": 1, "msg": "找不到"}           # 还有的地方这样
```

前端拿到三种完全不同的结构，只能写一堆 `if` 去猜。

**统一之后**：所有错误都是同一个形状，**前端只判断一个字段**。

```json
{ "success": false, "code": "KB_NOT_FOUND", "message": "知识库不存在", "detail": null }
```

**关键设计点**（这三个要能讲）：

1. **业务错误码用字符串不用数字**：`KB_NOT_FOUND` 比 `1002` 好——日志里一眼能看懂，不用查表
2. **区分"用户错误"和"系统错误"**：用户传错参数 → 4xx，附带你哪里错了；系统内部炸了 → 5xx，**给用户看通用提示，真实堆栈只进日志**（不然会泄露内部结构，也是安全问题）
3. **全局兜底处理器**：没被捕获的异常统一转成 500，避免把 Python traceback 直接吐给用户

### Q4：健康检查到底检查什么？

**新手写法**：

```python
@app.get("/api/health")
def health():
    return {"status": "ok"}
```

**问题**：这句话的意思是"我的 Web 框架起来了"。但 Web 框架起来了**不代表系统能用**——MySQL 挂了、Ollama 没启动、rerank API Key 过期了，这个接口照样返回 `ok`。

**正确做法：依赖探活**。

```
GET /api/health          → 快速返回（不查依赖），给负载均衡用
GET /api/health/deep     → 真的去探每个依赖，返回明细
```

```json
{
  "status": "degraded",
  "dependencies": {
    "database":  { "status": "ok",      "latency_ms": 3 },
    "ollama":    { "status": "ok",      "latency_ms": 41 },
    "reranker":  { "status": "error",   "latency_ms": 5002, "error": "401 Unauthorized" }
  }
}
```

**为什么分两个接口**：快速那个会被监控系统每秒调，不能每次都去连数据库；深度那个是人工排查和启动自检用的。

**`degraded` 这个状态是精髓**：依赖挂了但系统还能提供降级服务（比如 rerank 挂了，问答还能用无重排模式跑），这时状态是 `degraded` 而不是 `down`。**这直接对应规格表第 8 条**。

> 写这个接口时你已经提前回答了面试题"你怎么知道线上服务是好的"。

### Q5：为什么 `core/` 里的东西不许 `import` FastAPI？

因为 `core/` 是**可以脱离 Web 框架独立运行和测试的**。

M5 的评估脚本 `run_eval.py` 要跑几百次检索——它是**命令行脚本，不是 HTTP 请求**。如果 `core/retrieval` 里 `import` 了 FastAPI 的东西，这个脚本就没法干净地跑。

**同一个检索逻辑，两个入口**：

```
HTTP 请求  → api/v1/chat → services/chat_service → core/retrieval
评估脚本   → scripts/run_eval.py ────────────────→ core/retrieval
```

这就是分层的实际价值：**内核复用**。

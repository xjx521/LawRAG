# ADR-007：分工线——核心链路用户手写，样板代码助手给

> 状态：已采纳 · 2026-09-11

## 背景

用户是**准大四学生**，编程基础薄弱，会用基本语法但**无法独立完成项目**。同时明确要求：

> "保证我核心一定要会，而且**经得住问，从为什么这样设计开始**。"

这两个要求是**冲突的**：如果全部手写，进度会崩（24 个学习日做不完）；如果全部给代码，用户学不到东西，面试一问就露馅。

## 决定

**按"面试官会不会问"划分分工线。**

> **面试官会问的地方，用户写。不会被问的地方，助手给完整代码。**

| 用户手写（助手给骨架 + 留空 + review） | 助手给完整代码（用户读 + 改） |
|---|---|
| 混合检索、RRF、rerank、阈值、token 预算裁剪 | Dockerfile / docker-compose |
| 法条结构化解析（正则 + 五级层级 + 款/项 + "之一"） | Alembic 迁移脚本 |
| 评估指标计算（Recall@5 / MRR / Hit@1 / Citation F1） | Pydantic schema、ORM 模型定义 |
| 引用三层校验器 | FastAPI 路由骨架、config、日志配置 |
| Agentic RAG 的图 + 工具 + 护栏 | Streamlit 重复部分 |
| trace 计量逻辑 | 测试脚手架 |

### 判断标准的依据

左边那列的每一项，都对应面试中**"讲讲你是怎么实现的"**这类问题——面试官要听的是算法/设计，不是"我调了个库"。

右边那列的共同点：**结果是标准的，没有设计空间**。比如 ORM 模型定义，字段已经定死了，写出来就是写出来，面试官不会问"你为什么这么定义 User 表"。Alembic 迁移脚本更是机器生成的。

### 代码引导三级（铁律）

延续 gowork 加速阶段已验证有效的机制：

| 级别 | 给什么 | 什么时候用 |
|------|--------|-----------|
| **【提示】** | 文字/伪代码说清"这一步做哪几件事" | **已见过**的概念，不给代码 |
| **【骨架】** | 给框架 + 关键行留空，用户填 | 概念懂但**第一次写** |
| **【示例】** | **新概念**的最小可跑示例（详细注释） | 完全没接触过的 API 结构 |

**三条附加铁律**：

1. **同一概念只给一次【示例】**，之后全靠【提示】/【骨架】
2. **【示例】只给到"看懂长什么样"，不含当天实验答案**
3. **用户写、助手 review、绝不代写核心链路**

### 每个模块的固定流程（不许跳步）

```
先讲为什么这样设计 → 再动手写 → 再写 ADR → 再拷问
```

这是用户那句"从为什么这样设计开始"的落地。**不许直接给代码然后说"你看这就是实现"。**

## 代价

- **进度比纯给代码慢**（预计慢 30-50%）→ 接受：这正是目的。给代码 5 天能做完的东西，自己写要 8 天，但面试时一个答得出一个答不出。
- **用户会写出有 bug 的代码**，review 要花时间 → 接受：debug 本身是学习。gowork 阶段的记录显示用户从错误里学得比从正确代码里学得多。
- **助手需要克制**：看着用户写得慢/写歪，很容易想直接给答案 → **这是本 ADR 存在的主要目的**，把"不代写"写成明文规则。
- **可能需要中途调整分工线** → 允许，但调整要更新本 ADR 并说明原因。

## 已知的用户薄弱点（review 时重点看）

| 薄弱点 | 具体表现 | review 重点 |
|--------|---------|------------|
| **能讲** | 理解简单但**讲不出来** | 每模块学完要求**用自己的话复述**，不打断，听完再纠正 |
| **能写** | 手写慢，拼写笔误多 | 盯 `Choram`/`Ebeddings`/`ciity` 这类拼写、缩进层级、变量名不一致 |
| **能扛边界** | 想不全 | 主动追问"10 万文档会怎样""断网会怎样" |

## 面试怎么答

这个 ADR 面试时不用答（是学习方法），但它的产物会体现出来：

> 面试官："你这个混合检索是怎么实现的？"
>
> 用户能从头讲到尾——因为没有现成代码给他抄，是他一行行写出来、调出来的。

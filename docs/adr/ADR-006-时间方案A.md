# ADR-006：时间方案 A（4 周跑 M0-M5+M7，第 5 周补 M6+M8）

> 状态：已采纳 · 2026-09-11

## 背景

用户开学后每天 4-5 小时。同时面临**毕业设计**（需要能演示 + 能写论文）和**求职**（2026 年 12 月，需要简历上有东西）。

项目有 9 个里程碑。问题是：**按什么顺序做，才能保证"任何时刻停下来，都有一份能用的成果"？**

## 备选

| 方案 | 顺序 | 风险 |
|------|------|------|
| **A. 先完整主链路** | M0→M1→M2→M3→M4→M5→M7 → 再 M6→M8 | 低（见下） |
| B. 按技术难度递增 | 先做简单的 | 做完一半发现检索效果不行，评估体系没搭，**不知道问题在哪** |
| C. 先做 Agent（M6） | 从最酷的开始 | Agentic RAG 依赖稳定的检索层，地基没打好就是空中楼阁 |

## 决定

**选 A。前 4 周完成 M0-M5 + M7，第 5 周补 M6 + M8。**

```
第1周  M0(2天) + M1(2天) + 1天缓冲
第2周  M2(4天) + 1天缓冲
第3周  M3(4天) + M4 开头
第4周  M4 收尾(1天) + M5(2天) + M7(2天)
第5周  M6(3天) + M8(2天)
```

### 排布逻辑

**关键洞察：第 4 周末结束时，项目已经是"完整的"。**

到那时你有的东西：能建知识库、能上传法规、能检索、能问答、**能拿出一份评估报告**、有演示界面。这已经是一份完整的简历项目和一份完整的毕设主体。

M6（Agentic RAG）和 M8（Docker/README/架构图）是**增量**，不是**前置**。所以：

> **任何时候进度崩了，砍掉的都是"锦上添花"，不是"地基"。**

反过来，如果把 M5（评估体系）放最后，那就是最危险的排法——因为**没有评估，前面做的所有检索优化都是"我感觉变好了"**。面试官只要问一句"你怎么知道"，整个项目就塌了。

### 砍的顺序（明确写死，避免临场纠结）

1. **M8 的测试**（先砍，Docker 和 README 保留）
2. **M7 的深度**（前端只保留主流程演示，砍掉花哨交互）
3. **M6 的反思节点**（保留 query 改写和 max_iterations，砍掉 self-reflection）

**M5 评估体系绝不砍。** 它是论文实验章的全部内容，也是"经得住拷问"的根基。

### 为什么 M7（前端）排在 M6（Agent）前面

因为答辩/演示需要界面，而 M6 是技术亮点不是演示必需品。且 M7 只有 2 天，早做早安心。

## 代价

- **M6 排到第 5 周**，如果前 4 周拖延，Agentic RAG 会被压缩甚至砍掉。→ 接受：Agentic RAG 是加分项，不是主体。**毕设主体是 RAG**（见 ADR-008）。
- **前 4 周没有 Agent 相关内容**，与用户 gowork 阶段学的 LangGraph 暂时接不上。→ 接受：M6 会用到，且届时是"把学过的东西工程化"，不是重新学。
- **每周留 1 天缓冲**，实际是 4 个学习日/周而非 5 个。→ 这是刻意留的，不算浪费。

## 面试怎么答

> "你这个项目做了多久？"
>
> 四周做出完整系统，第五周做的 Agentic 和交付。
>
> 但我想说的不是时长，是顺序。我一开始就确定了"第 4 周末必须是一个完整系统"——能建库、能检索、能问答、**能拿出评估报告**。Agentic RAG 和 Docker 是增量，排最后。
>
> 这样有个好处：进度如果崩了，我砍掉的是锦上添花的东西，不是地基。而我们做项目最容易犯的错，是把评估放在最后——那样前面所有的优化都变成"我感觉变好了"，面试官问一句"你怎么知道"就答不上来。所以我的评估体系是**前四周内必须完成的**，不砍。

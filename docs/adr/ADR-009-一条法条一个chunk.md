# ADR-009：分块策略——一条法条 = 一个 chunk，保留五级层级

> 状态：已采纳 · 2026-09-11

## 背景

分块（chunking）是 RAG 里最容易被忽视、但影响最大的一环。gowork 阶段（Day52）做过实验，结论是"分块比整段命中更准"，但那是**通用文本的分块**。

法律文本有一个通用分块器无法利用的性质：**它本来就是结构化的**。

## 备选

| 方案 | 做法 | 问题 |
|------|------|------|
| A. 固定字数滑窗 | `RecursiveCharacterTextSplitter(chunk_size=500, overlap=50)` | **会把一条法条从中间切开**，切出来的碎片没有条款号，无法引用 |
| B. 按章/节切 | 每章一个 chunk | 粒度太粗，一章可能几十条，检索命中了但拼进 prompt 的是几十条法条 |
| **C. 一条 = 一个 chunk** | 用正则按"第 X 条"切 | ✅ 见下 |
| D. 一条内再细分 | 按款/项切 | 太细——法条的**款之间有逻辑关联**（"前款""但书"），拆开就断了 |

## 决定

**选 C：一条法条 = 一个 chunk，metadata 保留 `编/章/节/条/款/项` 五级层级。**

### 三个理由

**1. 法条是天然的语义单元。**

一条法条 = 一个完整的法律规范。它不需要"切"，它本来就是这个粒度。用滑窗去切，相当于把一句话切成两半然后分别理解。

**2. 条款号是引用的锚点。**

用户要看到的是"依据《劳动合同法》第 19 条"，而不是"依据某段文字的第 2 个片段"。**有了 `article_no` 字段，引用才能精确到条**——这是规格表第 14 条（引用三层校验）的前提。

**3. 层级结构解决了"指代丢失"问题。**

法条里高频出现"前款""该款""但书"这类回指。如果只存条号，模型看到"前款规定的..."不知道指的是什么。所以 metadata 要带**章/节**——检索时可以把同一章的相关条文一起取出来作为上下文。

### 粒度必须做到"款"

这是本项目最关键的一条设计约束，来自一个具体用例：

> 《最高法劳动争议司法解释（一）》**第 32 条第 1 款**自 2025-09-01 起被《解释（二）》（法释〔2025〕12号）废止——**整条仍然有效，只有其中一款失效**。

只做到"条"粒度的系统，遇到这个问题的答案只能是"第 32 条已废止"或"第 32 条有效"，**两个都是错的**。

所以 `chunks` 表必须有 `paragraph`（款号）字段，且**时效性日期要能标到款级**。

### 数据结构

```
chunks 表关键字段：
  chapter       章
  section       节
  article_no    条号（含"之一"，如 "32"、"32之一"）
  paragraph     款号（条内第几款，1 起）
  item          项号（（一）（二））
  content       该 chunk 的正文
  promulgated_at / effective_at / expired_at   时效三日期
```

> ⚠️ 这里有个待验证的设计点：**一个 chunk = 一条，还是 = 一款？**
> 当前定的是**一条 = 一个 chunk**，款/项记在 metadata 里。这样 vector 检索命中一条，但**时效性可以按款过滤**。
> 如果发现长条文（列举式）超出 rerank 的 1024 token 限制，可能需要改成"一款 = 一个 chunk + 冗余存条号"。**M2 拿到语料跑完长度分布后再定**，届时要更新本 ADR。

## 代价

- **必须自己写解析器**，不能直接用 `RecursiveCharacterTextSplitter`。这是 M2 的核心工作量（4 天）。→ 这正是价值所在：**领域特化的东西才是简历上能写的**
- **解析器有边界情况**：
  - `第X条之一`（修正案增设新条不重排后续序号）—— 必须支持，排序时要插在"第X条"和"第X+1条"之间
  - 中文数字（"第十条"不写"第10条"）
  - 款项识别：款是**无编号的自然段**，项是 `（一）（二）`，目是 `1. 2.`
- **语料格式依赖**：解析器要吃结构化 Markdown。如果语料质量差（比如丢了款/项层级），解析结果就会退化。→ 所以 ADR-010 要求交叉校验语料。

## 面试怎么答

> "你的分块策略是什么？"
>
> 一条法条一个 chunk，不是固定字数滑窗。原因是法律文本本来就是结构化的——"第 X 条"就是这个领域天然的语义单元，我用正则按条切，而不是把一条从中间切成两半。
>
> 更重要的是**层级**。我的 chunk 的 metadata 带编、章、节、条、款、项五级。其中款这一级是必须的，因为法条可能**部分失效**。举个真实例子：最高法《劳动争议司法解释（一）》第 32 条的第 1 款在 2025 年 9 月 1 号被废除了，但整条还是有效的。如果我只做到"条"的粒度，面对这个问题只能说"第 32 条已废止"或者"有效"，两个答案都是错的。
>
> 而且条款号是我引用的锚点——用户要看到"依据劳动合同法第 19 条"，不是"依据第 2 个文本片段"。所以我宁愿花四天自己写解析器：这是领域特化的部分，通用分块器做不到。
>
> 代价是解析器要处理边界情况，比如"第 X 条之一"——修正案加新条的时候不重排后面的序号，所以排序要把"之一"插在两条之间。

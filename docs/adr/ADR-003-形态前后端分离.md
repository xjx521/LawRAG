# ADR-003：项目形态——FastAPI 后端 + Streamlit 前端

> 状态：已采纳 · 2026-09-11

## 背景

需要确定项目形态。用户的既有能力（gowork 第二阶段已学完 FastAPI + Streamlit + MySQL 全栈）是可复用的基础。

而且这个项目有两个"展示场合"：**答辩演示**（需要界面）和**面试技术深挖**（需要 API）。

## 备选

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A. FastAPI + Streamlit** | 复用手艺；API 可单测/可被 curl/可面试现场演示；Streamlit 快速出演示界面 | Streamlit 不是"正经前端"（但这不重要，见下） |
| B. 纯 CLI / 脚本 | 最快 | **答辩没法演示**；面试官看不到产品感 |
| C. FastAPI + React/Vue | 最像真实产品 | 用户前端能力不足，会吃掉大半时间，且与 AI 应用开发实习的目标无关 |
| D. 直接用 Dify / RAGFlow 搭 | 一天做完 | **这恰恰是简历上最不能写的**——面试官会问"你做了什么" |

## 决定

**选 A：FastAPI 后端 + Streamlit 前端，前后端分离。**

### 理由

1. **FastAPI 侧承载全部技术深度。** 面试关心的东西——分层架构、Provider 抽象、检索链路、评估接口、SSE 流式——全在 API 层。这一层可以写单测、可以被 `curl` 验证、可以现场跑。

2. **Streamlit 只负责"看得见"。** 答辩时需要的是"能演示建库→传文档→提问→看到引用高亮"这个流程，Streamlit 用 Python 就能做到，不需要写一行 JS。**前端不做深度，做深度的是后端。**

3. **明确不做的事**：不写 React、不做用户注册登录的完整体系、不做权限的细粒度设计。`users` 表只是为了演示多租户隔离（规格表第 6 条），不做真实的账号体系。

### 为什么不用 Dify/RAGFlow 搭

这是本项目最重要的一条边界：

> **能用现成平台搭出来的东西，写在简历上就是负分。**

面试官看到"基于 Dify 搭建的知识库"会问："那你做了什么？配置参数吗？"——这个项目存在的意义就是**把通用平台的黑盒拆开自己实现**，然后在拆开的过程中做出平台做不到的领域特化（法条粒度、时效性、引用校验）。

Dify/RAGFlow 在本项目里的角色是**参考实现**（学它们的结构决策），不是**依赖**。见 ADR-008 的参考项目表。

### 分层依赖规则

前后端分离之上，后端内部强制分层：

```
api → services → core → models
```

**单向，不允许反向 import**，用 `import-linter` 强制检查，违规直接报错。

借用 Dify 的做法（`backend-layers` 契约）。为什么值得做：分层靠自觉一定会烂，尤其是赶进度的时候。写成 CI 检查，就是"我不用记得，工具会记得"。

## 代价

- Streamlit 每次交互整个脚本重跑，交互体验一般，复杂前端做不了 → 接受，前端不是重点
- 多一个进程要维护（`docker compose` 里两个 service）→ 接受
- `import-linter` 在初期会经常报错（写代码时容易顺手反向 import）→ 这是**feature 不是 bug**，它就是在帮你守住边界
